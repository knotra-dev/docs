**Keep Knotra open. Connect your assistant. Review its work in the app.** This connection controls Knotra itself; [external MCP servers](/docs/guides/mcp-tools) give tools to pipeline blocks.

## Connect your assistant

1. In native Desktop, click **Settings** at the bottom left, then **Control Knotra with MCP**.
2. Click **MCP client configuration** to expand it.
3. Click **Copy configuration** below the configuration box.

<DocScreenshot src="/images/control-knotra.webp" width={1000} height={755} alt="Control Knotra with MCP settings with MCP client configuration expanded and Copy configuration below it" caption="Settings → Control Knotra with MCP → MCP client configuration → Copy configuration. The pictured paths are examples; copy your app's configuration." />

**Check:** the button changes to **Copied**. Keep Knotra open with your workspace loaded.

4. Open your assistant's MCP settings. Add the copied server configuration and connect it; the exact location depends on your assistant.
5. Ask the assistant to read `knotra://guide` and `knotra://schema/v1`, then send this request:

> List my model sources. Create a pipeline with an Answer model block that writes a greeting, followed by a Human review block receiving its text. Show it in Knotra and validate it. Wait for me before starting a run.

6. Return to Knotra and open the new pipeline. Click each block to check its instructions and connections before running.

<DocScreenshot src="/images/beginner-04-connect.webp" width={660} height={253} alt="An Answer model block connected to a Human review block on the Knotra canvas" caption="Example draft to check in Knotra: Answer → Human. Your assistant's exact block layout may differ." />

**Check:** the pipeline is visible in the app and the model output connects to the human input. Creating and validating a draft does not start a run.

Use the copied configuration; its bundled CLI and authenticated desktop bridge paths belong to your installation. Editing needs no engine. Running needs a configured engine and its dependencies.

## What the assistant can do

**Build pipelines · configure sources · connect the engine · run and inspect work.** Account login still requires you to complete the provider's sign-in. Saved API keys and tokens are write-only and never returned by list or read tools.

<summary>All 29 tools and engine operations</summary>

Current input schemas are available through MCP discovery.

| Task | Tools |
| --- | --- |
| Inspect and navigate | `app_status`, `app_navigate` |
| Create and edit pipelines | `pipeline_list`, `pipeline_get`, `pipeline_create`, `pipeline_update`, `pipeline_delete`, `pipeline_validate`, `pipeline_publish` |
| Configure model sources | `model_source_list`, `model_source_catalog`, `model_source_save`, `model_source_refresh`, `model_source_remove` |
| Complete account setup | `model_source_sign_in`, `model_source_sign_in_status`, `model_source_sign_in_cancel` |
| Configure external MCP servers | `mcp_server_list`, `mcp_server_discover`, `mcp_server_save`, `mcp_server_refresh`, `mcp_server_remove` |
| Manage the engine connection | `engine_status`, `engine_start`, `engine_stop`, `engine_connect`, `engine_disconnect` |
| Run and inspect work | `engine_call`, `artifact_download` |

`engine_call` accepts defined operations for profiles, resources, validation, publication, runs, step history, human requests, resolution, and artifacts. It does not accept arbitrary HTTP requests. An assistant can inspect resources, start a published pipeline, read a human request, and submit schema-valid output.

The assistant can supply credentials during setup, but reads do not reveal saved credentials. Source edits appear in Settings; the local engine applies them after unfinished runs complete.

</details>

## Edit without overwriting newer work

<details>
<summary>Revision checks, unsaved drafts, and conflicts</summary>

1. List pipelines, then read the complete target with `pipeline_get`.
2. Pass its exact `revision` as `expectedRevision` when updating or deleting. Omitted package fields are preserved; file contents use base64, including text files.
3. Read an unsaved draft before explicitly using `allowDirty: true`. Editing while someone types can return `busy`.
4. On a conflict, read the latest state and reconcile the change. Never overwrite an unseen revision.

Publishing checks the current revision and creates an immutable engine definition. **Publication alone does not start a run.**

Model-source and MCP-server edits, refreshes, and removals also need the latest `revision` as `expectedRevision`. New sources omit ID and expected revision. MCP refresh never grants newly discovered tools automatically.

</details>

## Recover an uncertain action

<details>
<summary>Retry IDs, app restarts, and large artifacts</summary>

| Action | Safe retry |
| --- | --- |
| Ordinary mutating control tool | Use the same unique `requestId` and identical arguments within the current app session. |
| Definitive `busy` rejection | Read the latest state and use a new request ID. |
| App restarted | List or read the affected pipelines and sources first. Session receipts do not survive restarts; an old ID cannot prevent a duplicate. |
| Engine write, including publish or mutating `engine_call` | Reuse its separate durable `operationId` only for the same command. |
| Respond to a human request | `requestId` identifies the human request; `operationId` identifies the durable response operation. |

`artifact_download` returns integrity-checked metadata and base64 content. Responses are limited to **8 MiB**, including encoding and metadata. Open or export larger files in the app.

</details>
